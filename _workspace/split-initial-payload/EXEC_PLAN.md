# EXEC_PLAN: split-initial-payload

- **타입**: fix
- **프로젝트**: project/dev-news
- **상태**: IN_PROGRESS

## 목표

`docs/index.html`(557KB)의 초기 전송량을 줄인다. 첫 화면 20줄을 보려고 30일치
353건의 요약 전문을 전부 받는 구조를 고친다.

## 배경 — 측정

`to_view_model()`이 기사마다 세 벌의 텍스트를 싣는다.

| 필드 | 용도 | 목록에 필요? |
|------|------|-------------|
| `snip` | 행에 보이는 140자 | **필요** |
| `body` | 요약 전문 `<p>` | 상세 패널 전용 |
| `why`  | 왜 중요한가 | 상세 패널 전용 |

`grep` 확인: `body`·`why`는 `showDetail()`에서만 쓰인다. 목록 렌더(`rowHTML`),
검색·필터(`visible()`는 `title+snip+from+tags`만 본다), 정렬 어디에도 안 쓰인다.
하루 60건씩 쌓이므로 30일이 꽉 차면 1MB를 넘어간다.

## 접근법

최근 N일분만 `body`·`why`를 인라인하고, 그보다 오래된 기사는 상세를 열 때
월별 샤드에서 가져온다. **가져오는 장치는 이미 있다** — 아카이브 검색 결과가
`openArchived(url, month)`로 `docs/data/articles/YYYY-MM.json`을 fetch해
`SHARDS`에 캐시하고 상세를 띄운다. 그 경로를 재사용한다.

목록·검색·필터는 `snip`만 쓰므로 동작이 바뀌지 않는다. 바뀌는 건 "오래된 기사의
상세를 처음 열 때 한 번 네트워크를 탄다"는 것뿐이고, 같은 달은 캐시된다.

`openArchived`에 `extra` 인자를 더해 목록이 이미 아는 메타(출처·발행시각·댓글수·
썸네일)를 넘긴다 — 안 그러면 지연 로딩분만 상세 표시가 빈약해진다.

## 단계별 계획

1. 테스트 작성(RED) — 경계 안쪽은 body 포함, 바깥은 제외, snip은 항상 유지
2. `render.py`에 `inline_days` 도입 (기본 3일)
3. `template.html` — `openDetail`이 body 없으면 `openArchived`로 위임,
   `openArchived`가 `extra` 병합
4. 재렌더 후 용량 측정
5. verify → 커밋 → complete

## 완료 기준

- [ ] 최근 3일 기사는 `body`·`why`가 인라인된다
- [ ] 그보다 오래된 기사는 `body`·`why`가 없고 `snip`·`title`·`tags`는 있다
- [ ] 검색·필터·정렬이 지연 로딩분에도 그대로 동작한다
- [ ] ~~`index.html` 40% 이상 감소~~ → **미달. 실측 25% (556,980B → 412,808B)**
- [ ] 기존 테스트 전부 통과 + ruff 통과

## 결과 — 기준 미달분 기록

40%를 잡았지만 25%에 그쳤다. 남은 413KB의 대부분은 `body`가 아니라 **353건분의
`snip`(140자) + 메타**다. 기사당 body·why는 492B인데 snip·메타가 958B다.

다만 이 변경의 실제 값어치는 **증가 곡선을 꺾은 것**이다. 지금은 11일치(353건)라
절감폭이 작지만, 30일이 꽉 차면(약 1,800건):

| | 30일 만재 시 추정 |
|---|---|
| 변경 전 | 약 2.65 MB |
| 변경 후 | 약 1.86 MB |

body·why는 이제 3일치(약 180건)에만 붙으므로 30일 누적과 무관해진다.

**남은 레버 (이번 범위 밖):** 1.86MB도 여전히 크다. 근본 해결은 목록 자체를
페이지네이션하거나 무한 스크롤로 바꿔 `snip`·메타도 지연 로딩하는 것이다.
화면 동작이 바뀌는 변경이라 별도 작업으로 분리한다.
