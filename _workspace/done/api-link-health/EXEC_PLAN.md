## 목표

무료 API 목록에 **실제로는 죽은 API**가 상당수 섞여 있다. public-apis README는
커뮤니티 갱신이 느려 도메인이 사라졌거나 404가 된 항목이 그대로 남는다.
무작위 60건 실측(2026-08-29): 도달 실패 4건 · 404 1건 → 약 8%가 죽은 링크.

살아있는지 직접 확인해 죽은 항목을 목록에서 빼고, 그 사실을 화면에 밝힌다.

## 접근법

**전수 확인이 아니라 회전 확인 + 캐시.** 2,008건을 매 회차 전부 두드리면
회차가 느려지고 상대 서버에도 무례하다. `data/api_health.json`에 URL별
결과를 남기고, 매 회차 **새 URL 우선 → 가장 오래 확인 안 된 URL** 순으로
정해진 예산(기본 600건)만 확인한다. 하루 3회 실행이므로 전수 1바퀴 ≈ 1일.

**오탐을 죽음으로 세지 않는 것이 핵심.** 실측에서 403·429가 나온 곳
(jooble, collinsdictionary, lviv)은 살아있는데 봇을 막은 것뿐이다.

| 판정 | 근거 |
|------|------|
| 살아있음 | 2xx·3xx, 그리고 401/403/405/429/451 등 "응답은 한다" |
| 죽음 | 404·410, DNS 실패·연결 거부·연결 타임아웃·SSL 오류 |
| 판단보류 | 5xx, 읽기 타임아웃 — 일시 장애일 수 있어 카운트하지 않는다 |

죽음 판정이 **연속 2회** 쌓인 URL만 목록에서 뺀다(한 번의 네트워크 사고로
목록이 뭉텅이로 사라지지 않게). 여기에 더해 한 소스에서 30% 넘게 빠지면
필터를 통째로 건너뛴다 — Actions 러너의 네트워크가 통으로 막힌 회차 방어.

살아있음이 확인되면 fails를 0으로 되돌린다(복구한 API는 다시 들어온다).

## 완료 기준

- 죽은 링크가 연속 2회 확인 뒤 `docs/data/apis.json`에서 빠진다
- 403/429/5xx는 절대 제외되지 않는다
- 확인 결과가 `data/api_health.json`에 누적되어 회차 간 이어진다
- 네트워크 사고로 한 소스가 통째로 사라지지 않는다
