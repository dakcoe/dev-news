# EXEC_PLAN: add-failure-alert

- **타입**: feat
- **프로젝트**: project/dev-news
- **상태**: IN_PROGRESS

## 목표

회차가 깨졌을 때 저장소에서 바로 보이게 한다. 실패(exit 1)뿐 아니라 **성공으로
찍히는 열화**(게시 건수 급감)도 잡는다.

## 배경

2026-08-12 01:02 KST 회차(run 31510062957)가 push 거부로 죽었는데 **하루 뒤에
사람이 눈으로 발견**했다.

정정할 점: GitHub는 예약 워크플로 실패 시 cron을 마지막으로 고친 사람에게 기본
이메일을 보낸다. 그러니 "알림이 아예 없다"는 건 사실이 아니다. 진짜 문제는
**묻힘**이다 — 메일함에서 놓치기 쉽고, 열어보기 전엔 무엇이 왜 깨졌는지 모른다.

더 큰 사각지대는 따로 있다. `if: failure()`는 exit 1일 때만 뛰는데 이 파이프라인엔
성공으로 끝나는 열화 경로가 셋 있다.

- `if not picked: return 0` — 새 기사가 없으면 정상 종료
- 요약 한도(429)에 걸리면 20건 중 일부만 게시하고 정상 종료 (SPEC 1.6)
- 커밋 스텝의 `변경 없음 — 커밋 생략`도 정상 종료

즉 "매일 도는데 조용히 3건씩만 올라오는" 상태를 아무도 모른다.

## 접근법

**채널은 GitHub 이슈.** 외부 서비스도 시크릿도 필요 없다 — 러너에 `gh`가 기본
설치돼 있고 `github.token`으로 된다. 저장소를 보는 흐름에 자연스럽게 들어온다.

**중복 방지가 핵심.** 그냥 `gh issue create`만 쓰면 3회 연속 실패에 이슈가 3개
쌓여서 그것도 결국 묻힌다. 열려 있는 같은 제목의 이슈를 찾아 댓글로 붙이면
이슈 하나가 "연속 몇 번 깨졌는지" 타임라인이 된다. 고치고 닫으면 다음에 새로 열린다.

**열화 판정은 Python에 둔다.** 임계값 비교를 bash에서 하면 config.yaml을 셸로
파싱해야 하고 테스트도 못 한다. `build.py`가 판정해서 `$GITHUB_OUTPUT`으로
`published`·`degraded`를 내보내고, 워크플로는 플래그만 본다.

## 단계별 계획

1. 테스트 작성(RED) — 출력 방출·임계 판정·워크플로 배선
2. `scripts/notify.sh` — 제목으로 중복 조회 후 댓글 or 생성
3. `build.py` — `emit_actions_output()`, 조기 반환 경로에도 적용
4. `config.yaml` — `alert.min_published`
5. `daily.yml` — `issues: write`, 실패 스텝, 열화 스텝
6. verify → 커밋 → complete

## 완료 기준

- [ ] 실패 시 이슈가 열리고, 연속 실패는 같은 이슈에 댓글로 쌓인다
- [ ] 게시 건수가 임계 미만이면 성공한 회차에도 알림이 간다
- [ ] `GITHUB_OUTPUT`이 없는 로컬 실행에서는 아무 일도 하지 않는다
- [ ] 기사가 0건인 조기 반환 경로에서도 신호가 나간다
- [ ] `permissions`에 `issues: write`가 있다 (없으면 403으로 조용히 실패)
- [ ] 기존 테스트 전부 통과 + ruff 통과
